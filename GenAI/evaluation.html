Building an Agent Evaluation System

In this session, we dive into the Proxima Health Systems example. Our goal is to build an AI agent that supports customer engagement workflows, including customer relationship management (CRM), follow-up emails, and related tasks. Once we developed the agent, an important question arises: How do we know that it is "doing a good job?" It is our job to come up with a way to understand how well the agent is performing and to identify ways to improve it. The evaluation process is the focus of today's session.

Learning Objectives

  • Understand how to build an evaluation pipeline in n8n
  • Decide between different choices of metrics

You’ll Need:

  • A CRM spreadsheet containing the columns date, account_name, contact, type, summary, needs, products, and next_steps. You can make a copy here.

Part 2: Adding an Evaluation Pipeline

Now, we want a formal way to test how well our agent works. To do so, we first need to understand what it means for our agent to work well.

We will use n8n’s evaluation nodes and triggers to let us test different outputs and see how well they do against our selected benchmarks. We consider two types of tasks:

  • Verifiable tasks can be checked automatically to determine if the agent is performing them correctly. For example, does the agent assign a conversation to the correct product category?
  • Non-verifiable tasks do not have a clear right or wrong answer. For example, does the agent’s conversation summary accurately reflect the transcript? Is the follow-up email appropriate for the scenario?

Both task types can be evaluated in n8n. For this walkthrough, we will focus on the correctness metric for verifiable tasks and LLM-as-a-judge for non-verifiable tasks:

  • Correctness metric: Each transcript is assigned to one product category: “Capital Equipment,” “Diagnostics,” “Consumables,” “Services,” or “Digital Ops.” Does the agent categorize the transcript correctly?
  • LLM-as-a-judge: The agent also generates a follow-up email. Is the email professional, and does it align with the tone and content we want our representatives to use?

Note

There is an important difference between human-in-the-loop and evaluation. Human-in-the-loop should not be used to fix systemic/recurring errors; these issues should be identified during evaluation and addressed by improving the system prompt. Instead, human-in-the-loop is intended to provide human oversight once we are already relatively confident that our agent is performing well.

In the following section, we first focus on the correctness metric.

Part 3: LLM-as-a-Judge

Correctness is not always applicable. For example, the agent also generates a description of each conversation, which would allow us to quickly understand the visit. We may want to evaluate how accurate or useful these descriptions are. This is a non-verifiable task: we cannot verify it using a simple correctness check, and there may not be a single correct answer.

To evaluate the agent’s output in this case, we can instead use another LLM as a judge. In this section, we will focus on evaluating the follow-up email generated by the AI.

Note that there is a way to do this using a Set Metrics evaluation node in n8n and choosing the metric Helpfulness (AI-based). However, we will not use this approach. We will do it in a different way that lets us log more information, including the reasoning of the judge agent.

Exploratory Content: Monthly CRM Updates

With the CRM data collected in the Google sheet Proxima Health Logging CRM, we may want to track how many records fall into each product category each month. We can build a workflow to generate these monthly summaries automatically.

Step 1: Schedule Trigger

  • Add node: Schedule Trigger
  • Set it up to trigger once per month. You can also specify the time at which it should execute.

Step 2: Retrieving Data

  • Add node: Google Sheets → Get row(s) in sheet
    • Choose the Proxima Health Logging CRM spreadsheet from before.

Step 3: Filtering

We now want to only look at rep visits in the past month.

  • Add node: Filter

    • For the first value, choose

      {{ $json.date }}

    • Choose Date & Time → is after

    • For the second value, choose

      {{ new Date(Date.now() - 30*24*60*60*1000).toISOString() }}

      This represents 30 days before the current time.

Step 4: Summarizing

Now, we want to count the number of rows by product category. Summarize lets us do operations such as summing, counting, and finding the minimum or maximum of a set of data.

  • Add node: Summarize
    • Aggregation: Count
    • Field: products
    • Fields to Split By: products - This means that we get one number for services, one number for capital equipment, and so forth.

Step 5: Aggregating

This is a common step for making our data easier to access. The Summarize node returns one JSON object for each category. To reference these values individually, we need to transform the data structure.

  • Add node: Aggregate
    • Aggregate: All Item Data (Into a Single List)
    • Put Output in Field: data
    • Include: All Fields
  • What it does: Convert the JSON objects into a single list, allowing us to reference each category individually.

Step 6: Email

  • Add node: Gmail → Send a message
    • Resource: Message
    • Operation: Send
    • To: your choice
    • Subject: you can chose something like “Monthly CRM Report”
    • Email Type: Text
    • Message:
